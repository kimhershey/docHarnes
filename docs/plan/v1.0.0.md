## 1. PPTX 변환본이 PowerPoint와 다르게 보이는 문제

사용자 보고(0.8.2): 문서함에서 PPTX를 열면 **배경이 안 보이고, 차트와 표가 제대로 그려지지 않는다.**

DocuLens에는 PowerPoint 엔진이 없습니다. `documents/convert/pptx.rs`가 파일의 XML을 읽어 내부 모델(`DocModel::slides`)로 옮기고, `convert/html.rs`가 HTML로 다시 그린 뒤 WebView2가 PDF로 인쇄합니다.
아래 세 가지는 이 자체 리더가 구현하지 않은 부분이며, 새 의존성 없이 보강할 수 있습니다.

| # | 항목 | 지금 동작(코드 확인) | 할 일 |
|---|---|---|---|
| 1-1 | 배경 | `pptx::background_of`가 단색(`bgPr/solidFill`, `bgRef` 테마 색)만 읽는다. 그림 배경(`bgPr/blipFill`)·그라데이션은 버린다. `slide_shapes`는 슬라이드 자신의 도형만 그려서 마스터·레이아웃에 놓인 배경 그림·로고·띠가 나오지 않는다. | `Slide.background`를 색 / 그라데이션 / 그림으로 넓힌다. 마스터 → 레이아웃 → 슬라이드 순으로 자리표시자가 아닌 도형을 그린다(`showMasterSp` 반영). |
| 1-2 | 표 | `pptx::table`이 글·병합·열 너비·첫 행 머리글 여부만 읽는다. 셀 채움, 테두리, 행 높이, 표 스타일을 버리고 회색 선(0.5pt)과 회색 머리글로 통일한다. 기본 표 스타일은 머리글이 진한 바탕에 흰 글자라서, 바탕을 버리면 머리글이 잘 안 보인다. | `tcPr`의 채움·테두리(`lnL/R/T/B`)·세로 정렬·여백, `tr@h` 행 높이. `tableStyleId` — `ppt/tableStyles.xml`의 정의와 PowerPoint 기본 스타일(Medium Style 2 계열: 머리글·줄무늬·첫 열, 스타일의 글자색). `model::Cell`에 채움·테두리 필드 추가, HTML 출력 반영. |
| 1-3 | 차트 | `graphicFrame`의 차트는 "차트"라고 적힌 점선 틀(`ShapeKind::Placeholder`)만 남긴다. | 관계(rels)로 `ppt/charts/chartN.xml`을 찾아 저장된 값(`c:numCache` / `c:strCache`)으로 막대·가로 막대·선·영역·원형 차트를 SVG로 다시 그린다(제목, 범례, 축 이름, 계열 색은 테마 색). 그 밖의 종류는 데이터 표로 대신한다. 차트의 항목·값을 `DocModel::blocks`에도 넣어 검색·질문에 잡히게 한다. |

- **범위 밖**: 그림자·반사 같은 효과, 글꼴 대체로 생기는 줄바꿈 차이, 3D·복합 차트의 동일 재현, SmartArt, 애니메이션·전환. 구형 PPT(97–2003)는 글만 읽는 지금 상태를 유지한다.
- **검증**: 배경 그림·마스터 장식·스타일 표·차트를 담은 샘플 PPTX를 만들어 변환본(PDF → PNG)을 눈으로 확인하고 단위 테스트를 둔다. 실제 PowerPoint 화면과의 대조는 사용자 PC에서 한다(체크리스트 항목 추가).
- **순서 제안**: 표 → 배경 → 차트(차트가 가장 크다). 토큰을 아껴야 하면 표·배경만 먼저 내고 차트를 뒤로 미룬다.

## 2-1. 기존 문서를 서식 그대로 고쳐 저장하기 — 검토 결과 (2026-11-12, 실행 전)

**결론**: HWPX · DOCX · PPTX는 가능하다. 문서를 다시 만들지 않고 **원본 파일의 XML을 그대로 둔 채 고친 곳의 글자만 바꾸는 방식**이면 글씨체·크기·표·그림·쪽 설정이 원본 그대로 남는다.
이 방식은 이미 등록 양식 채우기(`generate/fill.rs`: zip의 다른 부분은 그대로 복사하고 본문 XML만 고쳐 쓰며, 표의 행을 본떠 늘린다)에 쓰고 있어 새 의존성이 필요 없다. HWP(바이너리)와 구형 DOC · PPT는 같은 수준으로는 어렵다.

지금 있는 "글자 수정"(`edit_text`, 뷰어의 글자 고치기)은 앱이 뽑아 둔 쪽 글(DB)만 고치고 원본 파일은 건드리지 않는다.

| 형식 | 서식 유지 수정 | 비고 |
|---|---|---|
| HWPX | 가능 | 고친 문단의 줄 배치 캐시(`hp:linesegarray`)를 지워 한컴오피스가 다시 배치하게 해야 한다(지금 코드는 다루지 않음 — 한컴오피스에서 확인 필요). |
| DOCX | 가능 | Word가 열 때 다시 배치한다. 목차·쪽 번호 같은 필드는 Word에서 갱신해야 한다. |
| PPTX | 가능 | 글상자·표의 글자. 글이 늘면 상자를 넘칠 수 있다(자동 맞춤 설정에 따름). |
| XLSX | 가능(셀 값) | 공유 문자열·셀 XML을 고친다. 수식 결과는 Excel이 다시 계산한다. |
| HWP 5.0 | 어렵다 | 압축된 레코드 스트림이라 글자 수·글자 모양 위치·줄 배치를 함께 고쳐야 하고, 쓸 수 있는 라이브러리(소스 공개 의무 없음)를 알지 못한다. 권장: 한컴오피스에서 HWPX로 저장한 뒤 수정. |
| DOC · PPT · XLS(구형) | 하지 않음 | 새 형식으로 저장한 뒤 수정. |
| PDF · 스캔 | 범위 밖 | 원본 서식을 가진 편집 대상이 아니다. |

수정 종류별로 서식을 맞추는 방법:

| 수정 | 방법 |
|---|---|
| 글자 바꾸기 | 그 글자가 든 run의 글자만 바꾼다. 글씨체·크기·색은 run에 붙어 있어 그대로 남는다. |
| 문단 추가 | 바로 앞(또는 지정한) 문단을 본떠 문단 속성·글자 속성을 그대로 쓰고 글만 넣는다. |
| 표의 값 · 행 추가 · 행 삭제 | 셀 글자만 바꾸거나, 기존 행을 본떠 넣는다(양식 채우기에 있는 방식; HWPX는 행 번호를 다시 매긴다). |
| 그림 교체 | 그림 파일만 바꾸고 틀(크기·위치)은 둔다. |
| 새 표 · 새 그림 삽입 | 문서 안의 기존 표·그림을 본뜰 수 있을 때만. 없으면 기본 서식으로 들어가 원본과 달라질 수 있다(뒤 단계). |

풀어야 할 문제:

1. **고칠 위치 찾기** — 화면에 보이는 것은 변환본(PDF)이라 원본 XML의 어느 문단인지 알아야 한다. 변환할 때 문단마다 원본 위치(부분 이름 + 문단 순번)를 기록해 두고 그 문단을 겨냥한다. 기록이 없는 기존 문서는 "바꿀 글이 문서에 한 번만 나올 때만 적용, 여러 번이면 묻기".
2. **쪼개진 글자** — 한 낱말이 서식이 다른 여러 run에 나뉘어 있을 수 있다. 문단의 글을 이어 붙여 위치를 찾고, 바뀐 글은 첫 run에 넣고 나머지에서 지운다(첫 run의 서식을 따름).
3. **다시 배치되는 것** — HWPX의 줄 배치 캐시, 목차·쪽 번호·상호 참조. 앱은 값을 고치지 않고 오피스 프로그램이 열 때 갱신하게 둔다.
4. **손대지 않는 문서** — 변경 내용 추적이 켜진 문서, 암호·배포용(보호) 문서, 전자서명 문서(서명이 깨짐), DRM으로 감싼 파일(읽을 수 없음).

안전장치: 원본을 덮어쓰지 않고 수정본을 새 파일로 저장해 같은 문서의 새 판(`doc_versions`)으로 등록한다. 적용 전에 바뀌는 문장의 전·후를 보여 주고 확인받는다. 저장한 뒤 앱의 리더로 다시 읽어 의도한 곳만 바뀌었는지 자동으로 대조한다.

단계 제안(1.0.0 안에서):

1. 글자 바꾸기 + 새 판 저장 — HWPX · DOCX · PPTX.
2. 문단 추가·삭제, 표 행 추가·삭제(본뜨기).
3. 어시스턴트 명령("3조의 납품 기한을 12월 31일로 바꿔줘": 모델이 문단별 고친 글을 제안 → 전·후 미리보기 → 적용)과 뷰어에서 고친 글자를 원본에 반영.
4. 그림 교체, XLSX 셀.
5. (보류) HWP 바이너리 직접 수정 — 따로 조사한 뒤 결정.

확인하지 못한 것: 수정한 파일을 한컴오피스 · Word · PowerPoint가 문제없이 여는지는 이 환경에서 볼 수 없다(사용자 PC 체크리스트로 확인). `linesegarray`를 지웠을 때 한컴오피스가 다시 배치하는지는 실제 프로그램으로 확인해야 한다. 외부 자료는 조회하지 않았다.

사용자 결정(2026-11-12):

- **기본값은 꺼짐** — "기본 꺼짐". 지금은 단계 목록이 항상 보이므로 1.0.0부터 기본 동작이 달라진다(릴리스 노트의 "동작이 달라지는 점"에 적는다). 0.8.x에서 올라온 작업 공간도 꺼짐으로 시작한다.
- **중요한 동작은 항상 보여 준다** — "맞음. 중요한 동작들은 항상 보여주기." 삭제·이동·이름 변경·설정 변경처럼 확인 카드가 뜨는 플랜(`requires_confirmation`)은 설정과 무관하게 단계 목록을 보여 준다.

- 경고 줄(범위를 채웠다, 유형 조건을 뺐다 등)은 단계 목록과 별개로 계속 보여 준다.

구현할 때 확인할 것:

- "중요한 동작"의 기준은 `requires_confirmation` 하나로 둔다(부작용이 있는 op, 근거 없는 설정 변경, 채우지 못한 요청이 모두 여기로 모인다). 설정 값 변경은 빠른 경로에서 확인 없이 실행되는 경우가 있는데, 이때도 전·후 값 카드는 그대로 보여 준다.
- 단계 목록을 전제로 한 E2E(`plan-step-*`를 기대하는 테스트)는 기본값이 바뀌므로 설정을 켜고 돌리거나 기대값을 고친다.

## 6. 문서 안 그림의 글자 인식

사용자 보고(2026-11-12, 0.8.2): "PDF/PPT 등 문서 내에 있는 그림에서 글자가 정상적으로 인식되지 않음." 모델은 프로젝터(`mmproj-F16.gguf`)와 함께 정상 로드된 상태였다(설정 화면 확인).

### 원인 (코드 + 실제 모델 재현)

- 글자 레이어가 있는 쪽(`text_source` = `layer`: 디지털 PDF, `converted`: PPT · DOCX · HWP 변환본)은 기본 설정(`processing.ocr_digital_pdf = false`)에서 OCR 대상이 아니다(`pipeline/run.rs`의 OCR 단계).
- 쪽 안의 그림만 읽는 경로가 없다. PDFium의 그림 개체(`page.objects()`)를 쓰는 코드가 없다.
- 그래서 그림 속 글자는 쪽 글·글자 레이어·검색 색인 어디에도 들어가지 않는다.

재현(Gemma 4 E4B Q4_K_M + mmproj-F16, CPU, 구성도와 표가 든 그림 1개를 넣은 A4 한 쪽; 그림 속 문자열 24개가 쪽 글에 들어왔는지):

| 입력 | 처리 | 그림 속 문자열 | 본문 | 걸린 시간(분류 + OCR + 추출) |
|---|---|---|---|---|
| 글자 레이어가 있는 PDF(기본 설정) | OCR 안 함 | 0/24(본문에도 있는 낱말 1개 제외) | 그대로 | 298 s |
| 같은 쪽을 스캔한 이미지 | 쪽 전체 OCR | 24/24 | 한 낱말이 바뀜("구간별" → "구성별"), 구성도가 표 하나로 뒤섞임 | 531 s |
| 그림만 따로 | 그림 OCR | 23/24("SMS·메일" → "SMS-메일") | 해당 없음 | 285 s |

- 이 샘플에서는 쪽 전체 OCR도 그림 속 글자를 읽었다. "쪽 전체로는 작은 글자가 안 읽힌다"는 것은 확인되지 않았다(더 작은 글자·더 빽빽한 쪽은 재지 않았다).
- 쪽 전체 OCR은 글자 레이어의 정확한 본문을 모델이 다시 읽은 글로 바꾼다. 그림만 읽으면 본문은 그대로 남는다.
- 조사 중 확인한 다른 경우: 프로젝터 없이 이미지를 보내면 0.3초 만에 `image input is not supported - hint: … you may need to provide the mmproj`로 실패한다. 프로젝터가 있으면 이미지 OCR 자체는 정상이다(한국어 샘플 이미지의 글·표 전부 인식).

### 사용자 결정 (2026-11-12)

1. **쪽 전체가 아니라 그림만 OCR한다** — "전체가 아닌, 이미지 파일만을 OCR 하면 되지 않는가?"
2. 아이콘·로고·장식선처럼 작은 그림은 건너뛰고, 모든 쪽에 반복되는 로고는 한 번만 읽는다 — "동의".
3. 읽은 글자를 쪽 글 뒤에 "[그림] …"으로 덧붙이는 방식은 **불허**. **문서함의 문서에서 그림 안의 글자를 드래그해 선택할 수 있어야 한다.**
4. 차트를 그릴 때 넣는 글자도 문서함에서 드래그하거나 수정할 수 있어야 한다.
5. 스캔 PDF는 우선 이미지 전체를 OCR한다(지금 동작 유지).
6. 그림 OCR을 켤지는 **처리 설정의 항목**으로 둔다 — "처리 설정에 추가해줘". 표시 문구는 "이미지 내 글자 추출", 기본값은 꺼짐.

| 6-1 | 쪽 안의 그림 찾기 | PDFium `page.objects()`의 그림 개체와 그 위치(쪽 좌표). 변환본도 PDF라서 PDF · PPTX · DOCX · HWPX · HWP에 같은 경로를 쓴다. 변환본 PDF에서 그림 개체가 한 덩어리로 나오지 않으면 변환 모델(`DocModel`)의 그림 위치를 쓴다. |
| 6-2 | 읽을 그림 고르기 | 최소 크기(쪽 대비 면적·픽셀) 미만과 극단적인 가로세로비(장식선)는 건너뛴다. 내용 해시가 같은 그림은 문서 전체에서 한 번만 읽고 결과를 다시 쓴다(반복 로고). 쪽·문서당 상한. 기준값은 실제 문서로 정한다. |
| 6-3 | 그림 OCR | 그림 영역을 쪽 렌더에서 잘라(또는 내장 비트맵으로) 모델의 이미지 한도 안에서 준비해 OCR한다. 그림용 지시문(글자가 없으면 `null`). 그림 하나에 모델 호출 한 번 — 작업 진행에 "그림 n/m" 표시. |
| 6-4 | 글자 레이어에 넣기(드래그 선택) | `layout::estimate(그림 조각, 읽은 글)`로 조각 안의 낱말 상자를 추정해 쪽 좌표로 옮기고, 쪽 레이아웃(`pages.layout`)에 합친다. 쪽 글(`pages.text`)에는 표식 없이 읽기 순서상 그림 자리에 넣는다(`layout::add_words`와 같은 규칙: 그림 상자 아래 첫 낱말 앞). 그러면 뷰어의 드래그 선택·글자 수정(기존 기능)·검색·질문이 그림 글자에도 그대로 된다. 그림 글자는 위치가 추정임을 낱말 단위로 표시한다(레이어 낱말과 구분). 어느 그림을 읽었는지(상자 + 해시)를 기록해 다시 읽지 않게 하고, 강제 다시 처리 때만 새로 읽는다. |
| 6-5 | 실행 시점 · 처리 설정 | 처리 파이프라인의 OCR 단계에서 "글자 레이어가 있는 쪽 + 6-2를 통과한 그림"에 실행한다. **설정 > 처리에 스위치를 추가한다**(표시 문구는 **"이미지 내 글자 추출"** — 사용자 지정 2026-11-12; 영어 짝은 "Extract text in images"(안), 키 `processing.ocr_figures`; 코어 `settings.processing`의 필드 + 설정 화면 + `ko.json` / `en.json`). 같은 키를 `planner::settings_catalog`에 등록해 어시스턴트에게 말로도 바꿀 수 있게 한다("이미지 내 글자 추출 켜줘"; 설정 목록의 라벨도 같은 문구, `src/lib/settingsCatalog.json` 다시 생성, 빠른 경로 낱말, 골든셋 문장). 스위치 설명에 "그림마다 모델을 한 번 부르므로 CPU에서는 문서당 수 분이 더 걸립니다"를 적는다. **기본값은 꺼짐**(사용자 결정 2026-11-12 "기본 꺼짐으로 해줘") — 켜기 전까지 처리 시간과 결과가 지금과 같다. 스위치를 켠 뒤 이미 처리한 문서는 다시 처리해야 그림 글자가 들어온다는 점을 화면에 안내한다. |
| 6-6 | 차트의 글자(1-3과 연결) | 차트를 SVG로 다시 그릴 때 제목·축 이름·범례·값 라벨을 실제 글자(`<text>`)로 그려 변환 PDF의 글자 레이어에 들어가게 한다(그림으로 굳히지 않는다). 그러면 뷰어에서 드래그 선택·수정이 기존 레이어 경로로 된다. SmartArt · OLE는 파일에 미리보기 그림이 있으면 6-1 ~ 6-4 경로로 읽는다. |
| 6-7 | 스캔 PDF · 사진 | 지금처럼 쪽 전체를 OCR한다. 쪽을 나눠 읽는 방식은 하지 않는다(보류). |
| 6-8 | 조사 중 찾은 결함 | ① 모델에 비전 프로젝터가 없으면 OCR·분류 전에 확인해 한국어로 안내한다(지금은 엔진의 영어 오류가 그대로 나온다). ② 쪽 이미지가 캐시에서 지워진 문서는 OCR을 오류 없이 건너뛴다(`run::page_image`가 파일이 없으면 넘어감) — 처리 전에 다시 렌더한다. |

검토에서 나온 위험:

- **낱말 위치의 정확도** — `layout::estimate`는 줄 단위(잉크 띠)로 글을 놓는다. 본문·표 같은 그림에는 맞지만, 상자 안 라벨이 2차원으로 흩어진 구성도에서는 낱말 상자가 어긋날 수 있다. 그림용으로 잉크 덩어리를 2차원으로 묶어 줄을 대응시키는 보강이 필요할 수 있다. 실제 문서로 확인한다.
- **읽기 순서** — 재현에서 쪽 전체 OCR은 구성도를 표 하나로 뒤섞었다. 그림만 읽으면 라벨이 줄 단위로 나왔다. 그림 글자를 쪽 글에 넣을 때 그림 하나를 한 덩어리로 유지한다.
- **수정의 의미** — 뷰어에서 고치는 것은 앱이 가진 쪽 글·레이어이고 원본 파일이나 그림 자체는 바뀌지 않는다(원본을 고쳐 저장하는 것은 2-1절).
- **구형 PPT** — 리더가 그림을 읽지 않아 변환본에 그림이 없다. 대상이 아니다(PPTX로 저장한 뒤 넣는다).

검증: 재현 샘플(그림이 든 PDF)로 그림 문자열이 쪽 글과 레이어에 들어가는지 단위·통합 테스트, 실제 모델 1회, 뷰어 E2E(그림 위를 드래그해 선택). 한컴오피스·PowerPoint 원본과의 대조는 사용자 PC 체크리스트.

하지 않을 것: "[그림] …" 표식으로 덧붙이기(불허), 글자 레이어가 있는 쪽을 통째로 다시 OCR하는 것을 기본으로 삼기(본문 글자가 바뀐다).

## 7. 문서 작성이 인용 문서 밖의 내용을 가져다 쓰는 문제

사용자 보고(2026-11-12, 0.8.2): "문서 작성에서 인용 문서 외의 문서들에서 내용을 가져다가 글을 작성하는 것을 확인함." 코드로 원인을 확인했다(실행 재현은 하지 않음).

원인(`generate/draft.rs`):

- 문서 작성의 "참고 자료 근거 사용" 스위치(`DraftRequest.use_knowledge`)가 **기본 켜짐**이다(코어 기본값과 화면 기본값 모두). 어시스턴트의 `draft_document`도 같은 기본값을 쓴다.
- 켜져 있으면 고른 문서와 별개로 지식 베이스를 검색해 찾은 대목을 글감(source)으로 넣는다 — 내용 칸의 앞 300자로 한 번(최대 4개 대목, `gather_sources`), 절별 생성에서는 절 제목으로 절마다 한 번 더(최대 3개, `draft_split`의 절 반복).
- 검색 범위(`knowledge_scope`)는 고른 문서로 제한되지 않는다 — 프로젝트가 있으면 그 프로젝트의 업무 문서 + 프로젝트 참고 자료 + 공통 참고 자료, 없으면 문서함 전체. 빼는 길은 초안의 "참고 문서" 목록에서 문서를 제외하는 것(`excluded_sources`)뿐이다.
- 고른 문서가 주는 내용은 적다(`document_source`) — 추출된 필드 값, 그리고 필드가 3개 미만일 때만 첫 쪽 본문의 앞 800자(`PAGE_TEXT_CHARS`). 그래서 본문 재료는 검색으로 딸려 온 다른 문서 쪽이 더 많아진다.

| # | 할 일 | 내용 |
|---|---|---|
| 7-1 | 고른 문서 안에서만 찾기 | 원본 문서를 골랐으면 내용·절별 검색의 범위를 그 문서들로 한정한다(`SearchScope.documents` = 고른 문서). 절마다 인용 문서의 관련 대목이 들어가고 다른 문서는 섞이지 않는다. |
| 7-2 | 고른 문서의 본문을 더 넣기 | "필드 3개 미만일 때 첫 쪽 800자" 제한을 없애고, 모델 컨텍스트 예산 안에서 고른 문서의 본문을 넣는다(길면 7-1의 문서 내 검색으로 절에 맞는 대목을 고른다). |
| 7-3 | 다른 문서 참고는 명시적으로 | 스위치를 기본 꺼짐으로 바꾸고, 켰을 때는 이름대로 참고 자료에서만 찾는다(업무 문서 제외). 문구도 무엇을 하는지 드러나게 고친다. 어시스턴트 경로의 기본값도 같이 바꾼다. |
| 7-4 | 출처 구분 표시 | 초안의 "참고 문서" 목록에서 "고른 문서"와 "검색으로 추가된 문서"를 구분해 보여 준다. |
| 7-5 | 테스트 | 문서 A만 고르고 비슷한 글이 든 문서 B가 문서함에 있을 때 B의 대목이 글감에 들어가지 않는지 단위 테스트(가짜 백엔드). |

- 7-1 ~ 7-3은 제안한 방향이고 사용자가 1.0.0 목록에 넣으라고 했다("지금 이 내용들을 1.0.0 에 추가해줘"). 7-3의 기본값(꺼짐)과 범위(참고 자료만)는 착수 때 확인한다.
- 지금 판에서의 우회: 문서 작성 화면에서 "참고 자료 근거 사용"을 끄거나, 초안의 "참고 문서" 목록에서 원치 않는 문서를 제외하고 다시 생성한다.

## 12. 문서를 프로젝트에 넣을 때 프로젝트 여러 개 선택

사용자 요청(2026-11-12): "문서들 프로젝트 일괄등록 할 때 프로젝트 여러개를 선택할 수 있도록 변경."

지금(`src/features/projects/PutInProjectDialog.tsx`, 문서함의 "프로젝트에 넣기"): 고른 문서들을 프로젝트 **하나**에만 넣을 수 있다(`projectId` 하나). 업무 문서 / 참고 자료 선택, 검색, 자동 분류 제안, 새 프로젝트 만들기가 같이 있다. 어시스턴트의 `add_to_project`도 프로젝트 하나를 받는다.

| # | 할 일 | 내용 |
|---|---|---|
| 12-1 | 프로젝트 여러 개 고르기 | 대화상자의 프로젝트 목록을 체크 목록으로 바꿔 여러 개를 고를 수 있게 한다(검색 유지, 9절의 전체 선택 / 전체 해제 부품). 확인하면 고른 문서들을 고른 프로젝트 각각에 넣는다(`projectAddDocuments`를 프로젝트마다 호출; 참고 자료면 각 프로젝트의 참고 자료 묶음에). |

### 12-B. 문서별로 넣을 프로젝트 지정 (배정표)

사용자 요청(2026-11-12): "파일을 여러개 선택하고, 각 문서들이 추가될 프로젝트를 문서별로 설정할 필요가 있을 것 같음. 예를 들어 문서를 200개 넣었는데 이 문서들이 일부는 AAA 프로젝트, 일부는 AAA 와 BBB 프로젝트, 일부는 AAA 와 CCC 프로젝트에 포함될 수 있을 경우를 처리할 필요가 있음." (지금은 코드 변경 없음, 설계만.)

12-1의 "고른 문서 전부를 고른 프로젝트 전부에"로는 이 경우를 처리할 수 없다. 문서마다 들어갈 프로젝트가 다르기 때문이다.

**바탕(코드 확인)**

- 한 문서는 여러 프로젝트에 속할 수 있다(`project_documents`의 키가 `(project_id, document_id)`). 데이터 구조는 바꿀 필요가 없다.
- (문서, 프로젝트) 쌍 목록을 한 번에 적용하는 함수가 이미 있다 — `projects::classify::apply(&[Assignment { doc_id, project_id }])`(자동 분류의 적용 단계).
- 자동 분류 제안(`Suggestion`)은 문서마다 제안 프로젝트 하나 + 다른 후보들(`alternatives`, 점수순) + 이미 든 프로젝트(`already_in`)를 준다.

**화면 — 배정표**

문서함에서 문서를 여러 개 고르고 "프로젝트에 넣기"를 열면 두 가지 방식 중 하나를 쓴다: "모두 같은 프로젝트에"(12-1) / "문서별로 지정"(이 절).

| 요소 | 내용 |
|---|---|
| 프로젝트 고르기 | 먼저 이번 작업에 쓸 프로젝트를 고른다(검색 + 체크, 예: AAA · BBB · CCC). 고른 프로젝트만 표의 열이 된다 — 프로젝트가 수십 개여도 열이 넘치지 않는다. 열은 나중에 더하거나 뺄 수 있다. |
| 표 | 행 = 고른 문서(이름, 유형, 폴더, 종류), 열 = 고른 프로젝트. 칸마다 체크 하나. **이미 그 프로젝트에 든 문서의 칸은 체크된 상태로 보여 주고, 체크를 풀면 그 프로젝트에서 뺀다**(사용자 결정). 새로 넣는 칸과 원래 들어 있던 칸은 모양으로 구분하고, 바뀐 칸(넣기 · 빼기)은 강조한다. 문서가 든 프로젝트 중 열로 고르지 않은 것이 있으면 자동으로 열에 더한다(가려진 소속이 없게). |
| 종류 열 | **문서마다 업무 문서 / 참고 자료를 고른다**(사용자 결정). 기본값은 그 문서의 지금 종류다. 여러 행을 골라 한꺼번에 바꿀 수 있다. |
| 열 머리의 체크 | 그 프로젝트를 지금 보이는 모든 행에 넣기 / 빼기. 예시의 "200개 전부 AAA"는 AAA 열 머리 한 번이다. |
| 행 여러 개에 한꺼번에 | 행을 여러 개 고른 뒤(체크, Shift로 범위, 걸러진 결과 전체 선택 — 9절 부품) "고른 행에 프로젝트 추가 / 빼기". 예시의 "일부는 BBB도"는 그 문서들만 걸러서 고른 뒤 BBB를 추가한다. |
| 거르기 · 찾기 · 정렬 | 이름, 폴더, 유형, 이미 든 프로젝트, "아직 아무 프로젝트도 지정하지 않은 문서만". 200개에서 묶음을 빨리 골라내는 수단이다. |
| 자동 제안으로 채우기 | 자동 분류의 제안을 체크로 미리 채운다. 1순위(제안 프로젝트)는 체크하고, **2순위 후보(`alternatives`의 첫째)는 점수가 기준 이상일 때만 함께 체크한다**(사용자 결정; 기준은 설정 항목이고 기본값 60 % — 아래 12-B-1). 3순위부터는 "후보" 표시만 한다. 제안으로 채운 칸은 사람이 고른 칸과 구분해 보여 주고, 사용자가 고친 뒤 확인한다. 이미 든 소속을 제안이 풀지는 않는다(빼기는 사람이 직접 체크를 풀 때만). |
| 요약 | 표 아래에 "AAA 200건 · BBB 60건 · CCC 45건 넣기, AAA에서 3건 빼기, 지정 안 된 문서 3건"처럼 프로젝트별 넣기·빼기 건수를 계속 보여 준다. 지정하지 않은 문서가 있으면 확인 전에 알린다(그대로 두는 것도 허용). |
| 확인 | 넣기와 빼기를 한 번에 적용하고 프로젝트별 결과(넣음 · 뺌 · 실패)를 보여 준다. **빼기가 한 건이라도 있으면 확인 단계에서 건수와 대상을 따로 보여 주고 한 번 더 확인받는다**(문서 자체는 지워지지 않고 문서함에 남는다는 안내 포함). 끝난 뒤 문서함에 머문다. |

**동작 규칙**

- 적용은 한 번의 요청·한 트랜잭션으로 한다(쌍 200 × n개도 즉시 끝난다). 프로젝트마다 따로 호출하지 않는다 — `classify::apply`를 일반 배정에도 쓰도록 이름·위치를 정리하고, 넣기 쌍과 빼기 쌍을 함께 받게 넓힌다(업무 문서는 `project_documents`, 참고 자료는 그 프로젝트의 참고 자료 묶음에서 넣고 뺀다).
- 업무 문서 / 참고 자료는 **문서마다** 정한다(종류 열). 그 문서가 들어가는 모든 프로젝트에 같은 종류로 들어간다 — 참고 자료면 프로젝트마다 그 프로젝트의 참고 자료 묶음에. 12-1의 "모두 같은 프로젝트에" 방식은 지금처럼 작업 전체에 하나를 고른다.
- 주의: 문서의 종류(`documents.role`)는 지금 문서 하나에 하나뿐이다(프로젝트마다 다른 종류는 0.8.0에서 남긴 PRJ-4). 이미 어떤 프로젝트에 업무 문서로 든 문서의 종류를 참고 자료로 바꾸면 그 프로젝트의 소속도 참고 자료 쪽으로 옮겨야 일관된다 — 종류를 바꾼 행은 요약에 "종류 변경 n건"으로 따로 보여 주고, 기존 소속을 함께 옮긴다. "AAA에서는 업무 문서, BBB에서는 참고 자료"는 이번 범위가 아니다(필요하면 PRJ-4와 함께).
- 방금 한 배정은 한 번에 되돌릴 수 있게 한다(넣은 쌍은 빼고, 뺀 쌍과 바꾼 종류는 되돌린다).
- 큰 목록: 가상 스크롤(문서함과 같은 방식), 머리 행과 문서 이름 열은 고정, 가로 스크롤은 표 안에서만 생기게 한다(11절). 키보드로 칸 이동·토글.

**이어지는 곳**

- 문서 추가(가져오기)가 끝났을 때 "가져온 문서 프로젝트 지정"으로 이 배정표를 바로 열 수 있게 한다 — 예시처럼 200개를 한 번에 넣은 직후의 흐름.
- 10절의 배지: 배정 뒤 문서 카드에 프로젝트 배지가 프로젝트마다 하나씩 나온다.
- 어시스턴트: 문서별 배정은 말 한 문장으로 표현하기 어렵다. "고른 문서 프로젝트 지정 화면 열어줘"로 배정표를 열고, "자동으로 프로젝트에 분류해줘"(`classify_projects`)는 지금처럼 문서당 프로젝트 하나를 제안한다. 한 문서를 여러 프로젝트에 자동 배정하는 것은 넣지 않는다(배정표에서 사람이 확인).

**테스트**: 코어 단위 테스트(쌍 적용: 넣기 · 빼기 · 중복 · 없는 프로젝트 · 참고 자료 묶음 · 종류 변경에 따른 소속 이동, 제안 채우기: 2순위 0.59는 체크 안 함 / 0.60은 체크), 모의 백엔드·E2E(문서 6개 · 프로젝트 3개로 예시의 세 묶음을 만들고 프로젝트별 문서 수와 배지 확인, 열 머리 체크, 걸러서 일괄 추가, 이미 든 칸의 체크를 풀어 빼기 + 확인 단계, 되돌리기), 문서 200개에서의 스크롤·넘침 확인.

**사용자 결정(2026-11-12)**: ① 종류는 문서마다 — "문서마다" ② 자동 제안은 2순위가 60 % 이상이면 2순위도 체크 — "2순위가 만약 60% 이상일 경우 2순위도 체크" ③ 이미 든 소속은 체크된 상태로 두고, 체크를 풀면 뺀다 — "이미 포함되어 있는 경우는 체크박스를 선택한 상태로 두어 체크를 해제할 경우 빼기".

**2순위 체크 기준은 설정 항목으로 둔다**(사용자 결정 2026-11-12: "설정에 추가해줘. 마찬가지로 자연어로 수정할 수 있도록 하네스에도 추가해주고").
