## 1. 하네스 설계 (검토 문서 §6)

### 1.1 순서 — 스키마를 의도한 순서로 내보낸다 (PLN-1)

- 원인: `serde_json::Value`의 맵이 알파벳순이라 `properties`가 알파벳순으로 직렬화되고 llama.cpp 변환기가 그 순서를 문법으로 고정한다.
- 수정: 엔진 요청을 만들 때 스키마를 **순서 보존 직렬화**로 쓴다. 규칙은 하나다. `properties`와 `required`를 함께 가진 객체는 `required`에 적힌 순서대로 속성을 쓰고, 나머지는 그 뒤에 쓴다.
  이 저장소의 문법용 스키마는 속성을 `required` 배열에 의도한 순서로 적어 두므로(플랜: summary 먼저, op 객체: `op` 먼저, 초안: title → fields → tables → body → notes) 빌더를 고치지 않아도 의도한 순서가 된다.
- 플래너·분류·추출·초안 등 `call_json`을 타는 모든 요청에 적용된다. 예시 응답(few-shot)도 같은 순서로 직렬화한다.
- `preserve_order` 기능은 쓰지 않는다(작업 공간 전체의 키 순서가 바뀜).
- 플랜 스키마: `summary → unmet → intent → scope → operations → requires_confirmation → confidence` + 선택 `clarification_question`.

### 1.2 글로 답하는 길 (USR-6, USR-3)

- 1단계 분류의 선택지에 `chat`(인사·감사·잡담)과 `general`(문서와 무관한 지식 질문)을 더한다. 이 둘이 나오면 2단계 플랜 호출을 하지 않는다.
- op는 늘리지 않는다(63개 그대로). 기존 **`answer`에 `mode: chat | general`과 `reply`(준비된 답)를 더한다.**
  (계획 초안은 새 op `reply`였다. 답변 실행·저장·대화 맥락을 이미 `answer`가 맡고 있어 같은 길에 방식만 더하는 쪽으로 구현했다.)
  - `chat`: 검색 없이 짧은 대화 프롬프트로 답한다. `reply`가 있으면(정해진 인사말의 빠른 경로) 모델 없이 그 글을 보인다.
  - `general`: 먼저 검색한다. 근거가 있으면 근거 답변, 없으면 일반 지식으로 답하고 "문서 근거 없이 답함"을 표시한다(요청 단위로 일반 지식 허용).
- 화면: `mode`가 있는 `answer`는 플랜 카드 없이 답변으로 바로 흐른다. `noop`뿐인 플랜은 모델 경로에서 `answer{mode: chat}`으로 바뀐다. 범위를 쓰지 않는 플랜에는 "대상 문서 N건"을 보이지 않는다.
- 문서 질문(`answer`, mode 없음)은 지금대로 근거 기반이다. 근거가 없으면 "근거 없음"과 "일반 지식으로 답하기" 버튼(기존).
- 붙여 넣은 글(다듬기·번역 등, PLN-16): 지시문과 본문 발췌만 플래너에 보내고(본문 전체를 `answer.question`에 옮겨 적다 응답 한도에 걸리는 일을 막는다),
  모델의 플랜이 문서함 요약·검색이면 `answer{knowledge:false}`로 바꾼 뒤 원문 전체를 되돌려 넣는다. 지시문에 다른 작업이 섞여 있을 수 있어 모델 호출 자체는 건너뛰지 않는다.

### 1.3 못 하는 요청의 길 (USR-7)

- 플랜에 **`unmet`**(문자열, 없으면 빈 문자열)을 둔다: 요청 중 op로 표현하지 못한 부분. 비어 있지 않으면 카드에 보이고 확인을 받는다.
- 프롬프트 규칙: "요청의 일부를 op 표로 표현할 수 없으면 가장 가까운 op로 대신하지 말고 `unmet`에 적거나 clarify로 선택지를 묻는다" + 예시.
- 사후 검증: 문장에 "~별", "마다", "각 …", "by …"가 있는데 플랜에 묶는 기준이 없을 때,
  op가 그 기준을 가지면(요약: 프로젝트·유형·폴더, 집계: 월·거래처·유형·프로젝트) 기준을 채워 넣고, 가지지 않으면(담당자별 등) `unmet`에 적고 확인 카드로 바꾼다. 규칙 경로의 플랜에도 같은 검사를 한다.

### 1.4 빠진 표현 (USR-7)

- `summarize`에 `group_by: none | project | doc_type | folder`를 더한다. 나누는 일은 실행기가 한다.
- `target = set`(묶음 하나)을 구현한다: 문서별 요약 → 묶음 요약. 지금은 두 분기가 같은 코드다.
- 결과: `{ summaries: [문서별], groups: [{ key, label, document_ids, summary }] }`.

### 1.5 근거 검증 (USR-1)

- 확인 없이 실행되는 변경(`set_setting`, `set_theme`, `set_language`, `set_profile`, `set_model`)은 대상 이름과 값이 문장에 있을 때만 바로 실행한다. 없으면 `requires_confirmation`과 경고 `ungrounded_change`.
- 모델이 적은 `confidence`는 자동 실행의 근거로 쓰지 않는다(0.6 미만이면 되묻는 기존 규칙만 유지).
- `set_setting`의 값은 문법에서 키별 타입으로 묶는다. 프롬프트에 `키 = 한국어 라벨` 표와 예시를 넣는다.
- 실행 결과: "UI 배율 100 % → 130 %" + 되돌리기.

### 1.6 빠른 경로 (USR-1, USR-2)

- `planner::fastpath`: 모델 우선 모드에서도 모델보다 먼저 본다. 출처 표시는 `fast`.
- 설정: ① 문장에서 설정 이름(라벨·별칭·동의어)을 하나만 찾음 ② 남은 부분이 그 키의 타입으로 읽히는 값 하나와 어미·조사뿐 ③ 값이 범위 안 ④ 물음이 아님. 하나라도 어긋나면 모델로.
  범위 밖 값은 실행하지 않고 범위를 알려 준다. 동의어는 설정 카탈로그에 둔다. '규칙(구형)' 모드도 같은 맞춤기를 쓴다.
- 인사말: 정해진 인사·감사는 `reply{chat, text}`로 바로 답한다.

### 1.7 측정 (PLN-21)

- 골든셋에 사용자 문장(설정 5, 인사, 프로젝트별 요약)과 변형, 반례를 넣는다. 빠른 경로는 단위 테스트와 CI 게이트로 고정한다.
- 평가 도구: 항목의 종류(대화·질문·명령·설정)별 정확도와 응답 시간, "확인 없이 실행됐을 잘못된 변경" 건수, 기대값의 `confirm`·`unmet`·`alt`, 일부만 돌리는 `--ids`·`--kinds`.
- 실제 모델 측정: `doculens-eval planner --engine …`(모델 우선 경로). 이 환경에서 Gemma 4 E4B Q4_K_M을 CPU로 돌려 0.7.0과 0.8.0을 비교하고 결과 파일을 `eval/results/`에 남긴다. 같은 명령을 사용자 PC 체크리스트에 넣는다.
- 실엔진 테스트(`tests/real_engine.rs`): 실제 llama-server의 문법 변환기를 거친 출력이 `summary`로 시작하고 op가 `op`로 시작하는지 확인한다(PLN-1 회귀 테스트).
- 모의 백엔드: 대화·일반 질문·반영하지 못한 부분·근거 없는 변경의 시나리오를 넣어 E2E로 고정한다.

## 3. 작업자 공통 규칙

1. `CLAUDE.md`를 먼저 읽는다. 맡은 항목은 `docs/audit/v0.7.0.md`에서 ID로 찾는다(문제·수정 방향·위치·확인 수준).
2. 확인 수준이 "점검 보고"나 "추정"인 항목은 **고치기 전에 코드나 테스트로 문제를 확인한다.** 문제가 아니면 고치지 않고 이유를 보고한다.
3. 원인을 가장 작은 변경으로 고친다. 가능하면 회귀 테스트를 붙인다(Rust 단위 테스트, vitest, 모의 백엔드 E2E).
4. 라이선스 규칙: 새 의존성은 계획에 적힌 것만(R3의 `tauri-plugin-single-instance`). UI 문자열은 한국어와 영어를 함께(`src/i18n/ko.json`, `en.json`).
5. Rust: 모든 cargo 명령 앞에 공유 빌드 설정을 불러온다. `cargo clean` 금지. 반복 중에는 `cargo check -p doculens-core`, 끝에 모듈별 테스트·`cargo fmt --all`·`cargo clippy -p <고친 크레이트> --all-targets -- -D warnings`.
   다른 작업자와 빌드 디렉터리를 같이 써서 "Blocking waiting for file lock"이 뜨면 기다린다.
6. 프런트: 워크트리 루트에 `node_modules` 심볼릭 링크를 건다(npm install 금지). `npm run typecheck`, `npm test`, 관련 E2E만 지정한 포트로 실행.
7. 커밋: 워크트리에서 항목 단위로 작게. 제목 `fix(<영역>): <무엇> (<항목 ID>)`. 본문 끝에 이 저장소의 공동 작성자·세션 줄 두 개. 푸시하지 않는다.
   `docs/HANDOFF.md`, `docs/audit/**`, `docs/plan/**`, `CLAUDE.md`, 버전 파일은 고치지 않는다.
8. 보고: 항목 ID별로 결과(고침 / 변경 불필요 / 일부 / 막힘), 바뀐 동작, 추가한 테스트, 커밋. 다른 작업자가 고쳐야 할 것, 추가한 i18n 키·모의 백엔드 변경, 위험을 적는다. 실패한 테스트는 출력과 함께 그대로 적는다.

## 4. 통합·검증·릴리스

1. 작업자 브랜치를 병합하고 충돌을 푼다. 고지·SBOM은 병합 뒤 `npm run notices`로 다시 만든다.
2. 리드가 하네스의 화면·모의 백엔드 연동을 얹는다(F3 병합 뒤).
3. 전체 검증: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`(PDFium 켬), `cargo deny check licenses`, 플래너 골든셋 게이트,
