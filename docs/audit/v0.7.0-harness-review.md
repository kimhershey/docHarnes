# 어시스턴트 하네스 검토 — 잘못 해석되는 근본 원인과 권장 구성

| | |
|---|---|
| 작성일 | 2026-11-11 (같은 날 2차 개정) |
| 질문 | ① 설정 문장은 규칙으로 먼저 해석할지, 문법만 고치고 모델에 맡길지 ② 근거 확인이 필요 없는 말을 판별하지 못하는 것과 잘못 해석되는 근본 원인은 무엇인지 |
| 상태 | **권장안입니다. 결정은 사용자가 합니다.** 코드는 고치지 않았습니다. |
| 관련 항목 | `docs/audit/v0.7.0.md`의 USR-1 · USR-3 · USR-6 · USR-7 · PLN-1 · PLN-20 · PLN-21 |

1차 판은 설정 문장만 다뤘다. 사용자가 스크린샷 두 장(인사말, "프로젝트 별 내용을 요약해줘")과 함께 "근본 원인은 해결되지 않는다"고 지적했고, 그 지적이 맞다.
2차 판은 근본 원인을 먼저 적고 권장안을 그에 맞춰 넓혔다.

## 1. 권장 (개정)

뿌리는 **모델에게 무엇을 말할 수 있게 해 두었는가**, 곧 출력 계약에 있다. 그래서 계약을 고치는 것이 먼저다.

**가. 출력 계약을 고친다 — 근본 원인**
1. **순서**: 해석을 먼저 쓰고, op 객체는 `op`부터 쓰고, 신뢰도는 맨 뒤로 보낸다.
2. **글로 답하는 길**: 인사·잡담·앱 사용법·일반 질문은 플랜을 만들지 않고 바로 글로 답한다.
3. **못 하는 요청의 길**: 요청을 op로 다 표현할 수 없으면 가장 가까운 op로 대신하지 않고 되묻는다. 플랜에 '반영하지 못한 부분'을 적는 칸을 둔다.
4. **빠진 표현을 채운다**: 요약에 묶는 기준을 넣고, 이름만 있던 '묶음 하나'를 실제로 구현한다.

**나. 실행 전 관문**
5. **근거 검증**: 확인 없이 실행되는 변경은 대상 이름과 값이 문장에 있을 때만 바로 실행한다. 모델이 적은 신뢰도는 기준에서 뺀다.
6. **비용 기준**: 문서 수만큼 모델을 부르는 작업은 규모를 보여 주고 "실행"을 한 번 눌러 시작한다.

**다. 빠른 경로**
7. 문장 전체가 "설정 이름 + 값" 꼴일 때, 그리고 정해진 인사말일 때만 모델 없이 처리한다.

**라. 측정**
8. 실제 모델로 재는 평가 세트를 둔다. 지금까지 모델 경로의 정확도는 한 번도 재지 않았다.

계약을 고쳐도 4B급 범용 모델은 일부 문장을 틀린다. 목표는 틀림을 없애는 것이 아니라 **틀려도 보이고, 싸고, 되돌릴 수 있게** 하는 것이고, 그 정도를 **재는** 것이다.

## 2. 근본 원인 — 모델이 틀린 것과 하네스가 막은 것

스크린샷의 플랜 요약 문장을 보면, 두 경우 모두 모델은 뜻을 알아들었다. 답을 담을 칸이 없었다.

| 사용자 문장 | 모델이 쓴 해석 | 실제로 일어난 일 | 원인 | 코드 |
|---|---|---|---|---|
| 안녕하세요. | "No operation requested, just a greeting." | 빈 플랜 카드와 결과 카드 | 대화 계열이 없고 글로 답하는 op가 없음 | `planner/prompts.rs:12-35`, `planner/mod.rs:737` |
| 프로젝트 별 내용을 요약해줘 | "모든 프로젝트의 내용을 묶음으로 요약합니다." | 문서 11건을 하나씩 요약하는 작업이 바로 시작 | 요약에 묶는 기준이 없음, '묶음 하나'는 미구현, 되묻기 규칙 없음, 자동 실행 | `planner/schema.rs:176-183`, `planner/exec.rs:679-712` |
| UI 배율 120% | 화면에 표시되지 않음 | "프로파일: 균형" 실행 | 문법이 `set_setting`을 `key`부터 쓰게 강제 | `planner/schema.rs:662` |

원인을 다섯 가지로 묶을 수 있다.

1. **출력 순서가 설계 의도와 반대다.** 스키마의 주석은 "summary가 먼저 나와 모델이 해석을 말한 뒤 op를 정한다"고 적는다. 그런데 스키마를 알파벳순으로 직렬화하기 때문에
   실제 문법은 confidence → intent → operations → requires_confirmation → scope → summary 순서를 강제한다. 모델은 **신뢰도를 가장 먼저, 해석을 가장 나중에** 쓴다.
   모든 문장에 해당하고, 맨 먼저 쓰는 신뢰도는 계획과 무관한 숫자가 된다.
2. **명령이 아닌 말의 출구가 없다.** 1단계 분류는 동작 계열 8개 중 하나를 반드시 고른다. 2단계는 op를 하나 이상 넣어야 하는데 글로 답하는 op가 없다.
   프롬프트는 모든 입력을 "명령"으로 규정하고 질문은 모두 근거 기반 답변으로 보낸다. 문서와 무관한 질문은 검색을 거쳐 "근거 없음"이 되고 버튼을 눌러야 일반 지식으로 답한다.
3. **표현할 수 없는 요청을 가장 가까운 op로 대신한다.** 요약의 선택지는 문서별과 묶음 하나뿐이다. 되묻기는 유형·양식·필드 이름이 목록에 없을 때만 하도록 적혀 있다.
   "프로젝트 별"을 담을 칸도, "이 부분은 못 한다"고 말할 칸도 없다.
4. **실행 기준이 부작용 유무와 자기 신뢰도뿐이다.** 신뢰도 0.6 이상이고 파일을 건드리지 않으면 바로 실행한다. 비용도, 해석이 맞는지도 보지 않는다.
5. **모델 경로를 재는 평가가 없다.** CI의 골든셋 게이트는 규칙 경로만 돈다. 실엔진 잡은 가중치가 무작위인 테스트 모델로 모양만 본다. 모의 백엔드는 규칙 파서의 해석을
   '모델' 출처로 보여 준다. 그래서 1번의 순서 문제가 처음부터 있었는데도 사용자 PC에서야 드러났다.

여기에 **모델 크기의 한계**가 겹친다. 스크린샷의 모델은 세 등급(E2B·E4B·12B) 가운데 E4B의 4비트 양자화다. 이 부분은 하네스로 줄일 수는 있어도 없앨 수는 없고, 이 환경에서는 재지 못했다.

1차 권장안(문법 수정, 근거 검증, 설정 빠른 경로)이 다루는 것은 1번의 일부와 4번의 일부다. 2번, 3번, 5번은 다루지 못했다.

### 설정 문장에 관한 사실

- **Home Assistant** (2024.12 릴리스 글): "빠른 내장 해석기를 먼저 겨냥하고, 맞는 것이 없을 때만 LLM 기반 에이전트로 넘긴다". 이유로 LLM이 "느리거나 비싸다"는 점과
  "집에서 말하는 명령의 90 %는 단순하다"는 점을 든다. 커뮤니티 보고에는 함정도 있다. 내장 해석기가 놓친 명령이 LLM으로 가서 수십 초가 걸리거나,
  LLM과 대화를 이어 가는 중에는 내장 해석기를 다시 보지 않는 경우다. **넘어간 뒤의 경로도 똑같이 정확해야 한다**는 뜻이다.
- **Windows 설정 에이전트**: 설정 전용 소형 모델(Mu)을 360만 건으로 학습해 수백 개 설정을 다룬다. 그런데도 Microsoft는 "여러 낱말의 뜻이 분명한 질의에서 가장 잘 동작하고
  짧거나 덜 쓴 입력은 맥락이 부족하다"고 보고, 짧은 질의는 종전의 검색 결과를 보여 주고 긴 질의에만 에이전트를 띄운다. 변경은 제안이고 사용자가 요청해야 적용된다.
- **Rasa CALM**: NLU 어댑터가 명령을 내면 기본값으로 LLM 호출을 건너뛰고, 둘이 충돌하면 어댑터가 이긴다. 문서는 위험도 적는다. 분류기가 약하면 엉뚱한 흐름이 시작된다.
- **FunctionGemma**: Google의 수치로 기본 모델 58 %, 대상 앱의 동작으로 미세조정한 뒤 85 %.
- **도구 정의 지침**: OpenAI는 한 번에 보이는 함수를 20개 미만으로(느슨한 권고), 열거형과 객체 구조로 "잘못된 상태를 표현할 수 없게" 하라고 한다.
  Anthropic은 겹치는 도구가 많으면 모델이 흐트러진다고 하고, 큰 도구 집합에는 필요한 것만 찾아 싣는 방식(내부 평가 49 % → 74 %)과 사용 예시를 권한다.
  엣지 기기 연구("Less is More", 8B 모델)도 보여 주는 도구 수를 줄이면 도구 선택 정확도가 오른다고 보고한다.
- **구조화 출력의 키 순서**: llama.cpp 변환기는 필수 속성을 스키마에 적힌 순서 그대로 고정한다(현재 소스에서 확인). Gemini 문서는 예시의 속성 순서가 스키마와 다르면
  출력이 "장황해지거나 예상과 달라질 수 있다"고 경고한다. 필드 순서의 영향은 연구마다 엇갈리지만, 영향이 있다는 쪽은 "답을 먼저 쓰게 하면" 작은 모델에서 크게 떨어진다고 보고한다.
  Gemma 4가 학습한 함수 호출 형식도 함수 이름이 인수보다 먼저 나온다.
- **모델의 자기 신뢰도**: 말로 표현한 신뢰도는 과신하는 경향이 여러 연구에서 반복된다.

### 명령이 아닌 말, 못 하는 요청, 오래 걸리는 작업에 관한 사실

- **도구 호출 API 전반**(OpenAI, Gemini, Mistral, Amazon Nova): 기본값은 모델이 도구를 부를지 **글로 바로 답할지** 스스로 고르는 것이다. 글 답변이 정식 출력이다.
  우리 플랜 문법에는 이 출구가 없다.
- **Rasa CALM**: 명령 어휘에 흐름 시작·값 채우기 말고도 주제 밖 대화(ChitChat), 지식 검색 답변(SearchAndReply), 되묻기(Clarify)가 들어 있다. 기본 패턴으로
  잡담, 지식 검색, **처리할 수 없음**(맞는 흐름도 관련 문서도 없을 때), **되묻기**(여러 흐름에 걸칠 때)가 따로 있다. 명령이 아닌 말과 못 하는 요청이 처음부터 어휘에 있다.
- **Adaptive-RAG**: 질문을 검색 불필요, 한 번 검색, 여러 번 검색으로 먼저 분류한다. 다만 논문은 분류기가 "검색 불필요"를 "한 번 검색"으로 47 % 혼동했다고 적는다.
  **분류만 믿지 말고 틀렸을 때 싸게 바로잡을 길**을 두어야 한다는 뜻이다.
- **LlamaIndex**: 요약용 엔진과 사실 검색용 엔진을 라우터로 가르고, 복합 질의는 하위 질문으로 쪼개 각각 보낸다. "프로젝트별"처럼 나눠서 처리할 일은 모델의 즉흥이 아니라 하네스의 기능이다.
- **딥 리서치 제품**: ChatGPT는 조사 전에 목표를 확인하는 질문을 할 수 있고 계획을 검토·수정하게 한다. Gemini는 편집 가능한 계획을 먼저 보여 준다. 오래 걸리는 일은 시작 전에 한 번 멈춘다.
- **Microsoft 사람-AI 상호작용 지침**: 불확실하면 되묻거나 서비스 범위를 줄인다(10번), 틀렸을 때 쉽게 고치게 한다(9번), 왜 그렇게 했는지 보인다(11번).

## 4. 공통점

1. **닫힌 목록은 결정적으로 먼저 본다.** 대상이 열거 가능하고 값에 타입이 있으면 규칙·검색·분류기가 먼저다.
2. **짧은 입력일수록 모델에 맡기지 않는다.** 전용으로 학습한 모델을 가진 Microsoft도 짧은 질의는 검색으로 처리한다.
3. **모델은 좁은 어휘로만 말하고 실행은 코드가 한다.** 그 어휘에는 "그냥 답하기", "되묻기", "못 한다"가 들어 있다.
4. **부작용과 비용은 등급을 나눠 확인한다.** 되돌릴 수 있고 근거가 분명하면 바로, 오래 걸리거나 불확실하면 한 번 멈춘다.
5. **평가 세트로 고정한다.** 고칠 때마다 실제 문장 세트로 잰다.

## 5. 설정 문장의 선택지 비교

| | 가: 문법만 고치고 모델에 맡김 | 나: 설정 문장은 규칙 먼저 | 다: 겹쳐 쌓기(권장) |
|---|---|---|---|
| 짧은 설정 문장의 정확도 | 미세조정 없는 4B급 모델에 달림. 실모델로 재 보지 못함 | 표에 있는 이름이면 확정 | 표에 있는 이름이면 확정, 나머지는 모델 |
| 틀렸을 때 | 엉뚱한 설정이 조용히 바뀜 | 규칙이 질문을 명령으로 오해할 수 있음 | 근거 없는 변경은 확인 카드 |
| 응답 시간 | 모델 호출 2회. 기록된 수치로 GPU 1~3초, CPU 10초 안팎 | 즉시 | 흔한 꼴은 즉시 |
| 모델이 없을 때 | 설정을 말로 바꿀 수 없음 | 가능 | 가능 |
| 2026-11-09 결정과의 관계 | 그대로 | 예외가 넓음 | 좁은 예외 하나 + 사후 안전장치 |

"가"의 약점은 문법을 고쳐도 남는다. 문법은 모양만 보장하고 고른 설정이 맞는지는 보장하지 않는다.
"나"의 약점은 2026-11-09에 겪은 것과 같다. 그때 걷어낸 것은 낱말이 들어 있기만 하면 잡는 규칙이었다. 여기서 권하는 것은 문장 전체가 맞아야만 잡는 규칙이다.

## 6. 권장안 상세

**1. 순서 (PLN-1)**
- 플래너 스키마와 예시 응답을 순서를 지키는 직렬화로 내보낸다. 최상위는 summary → intent → scope → operations → requires_confirmation → confidence. op 객체는 `op`가 첫 키.
- serde_json의 `preserve_order` 기능은 작업 공간 전체의 키 순서를 바꾸므로 쓰지 않고 플래너 스키마에만 적용한다. 추출·초안 스키마의 순서도 같은 방식으로 따로 본다.
- `set_setting`의 값을 키별 타입으로 묶는다(정수 범위, 참·거짓, 열거). 프롬프트에 `키 = 한국어 라벨` 표와 예시를 넣는다.
- 테스트: "직렬화된 스키마의 첫 속성이 summary", "모든 op 대안의 첫 속성이 op".

**2. 글로 답하는 길 (USR-6, USR-3)**
- 1단계 분류의 출력에 말의 종류를 먼저 적게 한다: 대화, 일반 질문, 문서 질문, 작업. 대화와 일반 질문이면 계열을 고르지 않는다.
- 대화(인사·감사·잡담·앱 사용법)는 2단계 플랜 호출 대신 짧은 답변 호출을 한다. 모델 호출 수는 그대로다. 카드와 "대상 문서 N건" 표시는 없다.
- 일반 질문은 정책에 따른다(§8의 결정 2). 답하는 쪽이면 "문서 근거 없이 답함" 표시를 붙인다.
- 문서 질문은 지금의 근거 답변이다. 분류가 틀릴 수 있으므로 답변 카드에 "문서에서 찾아보기"와 "일반 지식으로 답하기" 전환을 둔다. 뒤의 것은 이미 있다.
- 정해진 인사·감사는 모델 없이 답한다.

**3. 못 하는 요청의 길 (USR-7)**
- 프롬프트 규칙: "요청의 일부를 op 표로 표현할 수 없으면 가장 가까운 op로 대신하지 말고, 할 수 있는 선택지를 들어 되묻는다." 예시도 넣는다.
- 플랜에 '반영하지 못한 부분' 칸을 둔다. 차 있으면 카드에 보이고 자동 실행하지 않는다.
- 사후 검증: 문장에 "~별", "각각", "마다"가 있는데 플랜에 묶는 기준이 없으면 확인 카드로 바꾼다.

**4. 빠진 표현 (USR-7)**
- 요약에 묶는 기준(프로젝트·유형·폴더)을 넣는다. 나누는 일은 실행기가 한다.
- '묶음 하나'를 구현한다(문서별 요약 뒤에 합친 요약). 지금은 두 분기가 같은 코드다.
- 평가에서 실패한 문장을 보고 빠진 표현을 계속 찾는다.

**5. 근거 검증 (USR-1)**
- 설정·테마·언어·프로파일·모델 변경은 대상 이름과 값이 문장에 있어야 바로 실행한다. 숫자는 문장에 그 숫자가 있어야 한다. 없으면 확인 카드.
- 결과는 "UI 배율 100 % → 130 %"와 되돌리기 버튼으로 보인다.

**6. 비용 기준 (PLN-20)**
- 바로 끝나고 되돌릴 수 있는 것만 자동 실행한다. 문서 수만큼 모델을 부르는 작업은 규모를 보이고 "실행"을 눌러 시작한다. 기준 문서 수는 설정으로 둔다.

**7. 빠른 경로**
- 조건을 모두 만족할 때만 잡는다. ① 문장에서 설정 이름(라벨·별칭·동의어)을 하나만 찾음 ② 남은 부분이 그 키의 타입으로 읽히는 값 하나와 어미·조사뿐 ③ 값이 범위 안 ④ 물음이 아님.
- 하나라도 어긋나면 모델로 넘긴다. 범위 밖 값은 실행하지 않고 범위를 알려 준다. 이름만 있으면 현재 값과 설정 위치를 보여 준다.
- 동의어는 설정 카탈로그에 열로 둔다. 규칙 파일에 문장을 늘리지 않는다.

**8. 측정 (PLN-21)**
- 평가 도구의 실엔진 모드는 이미 모델 우선 경로를 탄다. 실제 모델로 골든셋을 돌리는 스크립트를 사용자 PC 체크리스트에 넣고 결과를 저장소에 기록한다.
- 사용자 문장(설정 5개, 인사, 프로젝트별 요약)과 변형을 골든셋에 넣고, 종류별 정확도와 응답 시간을 본다.
- 모의 백엔드에 "모델이 틀리게 해석한 경우"를 넣어 확인 카드 흐름을 E2E로 고정한다.

## 7. 권하지 않는 것

- **낱말 포함 규칙의 부활**: 2026-11-09에 걷어낸 방식이다.
- **모델 미세조정**: 효과는 크지만 레지스트리의 공개 GGUF를 그대로 쓰는 지금 구조와 맞지 않는다.
- **llama-server의 네이티브 도구 호출로 전환**: Gemma 4 형식의 파서 지원이 빌드마다 다르다는 보고가 있다. 엔진 태그를 올릴 때 다시 본다.
- **신뢰도 숫자로 자동 실행 여부를 정하는 것**.
- **플랜을 검사하는 모델 호출을 한 번 더 넣는 것**: 응답 시간이 늘고, 작은 모델의 자기 검사는 믿기 어렵다. 결정적 검증과 사용자 확인으로 대신한다.

## 8. 결정이 필요한 것

1. **설정의 좁은 빠른 경로**를 둘지. 2026-11-09의 모델 우선 결정에 예외를 하나 더하는 일이다.
2. **일반 질문에 답하게 할지.** 지금 기본값은 일반 지식 꺼짐이다. 문서 근거를 원칙으로 한 선택이었다. 대화(인사·앱 사용법)는 이 정책과 무관하게 답하도록 권한다.
   문서와 무관한 지식 질문은 ① 표시를 붙여 바로 답 ② 지금처럼 "근거 없음"과 버튼 중에서 고른다.
3. **오래 걸리는 작업의 자동 실행을 끌지**, 끈다면 기준 문서 수.
4. **버전**: 출력 계약 변경은 구조 변경이라 규칙대로면 마이너 버전이다. 사용자 보고 결함의 수정이기도 해서 0.7.1에 함께 넣는 쪽을 권한다. 나눈다면 §6의 1·5·6·7·8번을 0.7.1에, 2·3·4번을 0.8.0에 둔다. 그 경우에도 인사말에 빈 카드가 뜨지 않게 하는 최소 수정은 0.7.1에 넣는다.

## 9. 확인하지 못한 것

- 실제 Gemma 4 모델로 고친 뒤의 정확도를 재지 못했다. §6의 8번이 그 측정이다.
- 이 세션의 네트워크 정책으로 원문 사이트 여럿을 직접 열지 못했다(blogs.windows.com, rasa.com, ai.google.dev, blog.google, www.home-assistant.io).
