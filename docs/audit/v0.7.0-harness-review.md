# 어시스턴트 하네스 검토 — 설정 문장을 어떻게 해석할 것인가

| | |
|---|---|
| 작성일 | 2026-11-11 |
| 질문 | 설정 문장은 규칙으로 먼저 해석할지, 문법만 고치고 모델에 맡길지 (`docs/audit/v0.7.0.md`의 USR-1, "결정이 필요한 것" 3번) |
| 상태 | **권장안입니다. 결정은 사용자가 합니다.** 코드는 고치지 않았습니다. |

## 1. 권장 — 둘 중 하나가 아니라 세 겹

1. **문법과 프롬프트를 바르게 고친다(필수).** op 객체는 항상 `op`부터, 예시도 같은 순서로. 이것은 선택과 무관한 결함 수정이다(PLN-1).
2. **모델이 낸 '확인 없이 실행되는' 변경은 문장에 근거가 있을 때만 바로 실행한다(필수).** 설정 이름과 값이 문장에 없으면 확인 카드로 바꾼다.
   모델이 스스로 적는 신뢰도는 실행 기준으로 쓰지 않는다. 이미 있는 사후 안전장치(`planner::guard`)와 같은 자리이고 "모델 우선" 원칙을 건드리지 않는다.
3. **문장 전체가 "설정 이름 + 값" 꼴일 때만 모델 없이 처리한다(권장, 좁게).** "UI 배율 120%", "프로파일 정확도", "DPI 200으로 바꿔줘" 같은 문장이다.
   설정 카탈로그(46개 키의 라벨·타입·범위)가 이미 있어 그 표로 맞춘다. 조금이라도 애매하면 모델로 넘긴다.

3번은 2026-11-09의 "모델 우선" 결정에 좁은 예외를 하나 더하는 것이다. 지금도 슬래시 명령과 단독 "취소"는 규칙으로 먼저 처리한다. 같은 급의 예외다.
그때 문제가 된 것은 **낱말이 들어 있기만 하면 잡는 규칙**이었다("합계", "찾아"가 든 질문을 명령으로 오해). 여기서 권하는 것은 **문장 전체가 맞아야만 잡는 규칙**이다.

"문법만 고치고 모델에 맡긴다"만으로는 부족하다고 보는 이유는 §3과 §4에 있다.

## 2. 다른 소프트웨어는 어떻게 하나

| 소프트웨어 | 먼저 보는 것 | 모델의 역할 | 실행 전 확인 | 근거 |
|---|---|---|---|---|
| Home Assistant 음성 비서 | 문장 틀로 맞추는 내장 해석기 | 맞는 틀이 없을 때만 LLM으로 넘김 | 단순 기기 제어는 바로 실행 | 원문 확인 |
| Windows 11 설정 에이전트 | 짧은 질의는 일반 검색(낱말·의미) | 여러 낱말의 뜻이 분명한 질의만, 설정 전용으로 학습한 온디바이스 소형 모델 | 변경을 제안하고 사용자가 적용 | 검색 요약 |
| Rasa CALM (기업용 대화 프레임워크) | 선택형 NLU 어댑터가 먼저 명령을 냄 | LLM은 "흐름 시작·값 채우기" 같은 소수의 명령만 출력, 실행은 결정적 흐름 엔진 | 흐름에 정의 | 검색 요약 |
| Google FunctionGemma | 흔한 명령은 기기의 소형 모델 | 복잡한 것은 큰 모델로 넘김("교통 정리" 역할) | 앱이 정함 | 검색 요약 |
| VS Code | 설정 색인을 가진 `@vscode`, 설정 편집기의 AI 검색 | 설정을 찾아 줌 | "설정 편집기에서 보기" 버튼으로 사용자가 바꿈 | 검색 요약 |
| Apple App Intents | 앱이 타입 있는 인텐트·매개변수를 선언 | 시스템이 매개변수를 해석 | 모호하면 고르게 하고, 부작용이 있으면 확인 | 검색 요약 |
| MCP 명세 | — | 도구 호출 | "사람이 거부할 수 있어야 한다", 확인 프롬프트 권고 | 원문 확인 |

세부 사실.

- **Home Assistant** (2024.12 릴리스 글): "빠른 내장 해석기를 먼저 겨냥하고, 맞는 것이 없을 때만 LLM 기반 에이전트로 넘긴다". 이유로 LLM이 "느리거나 비싸다"는 점과
  "집에서 말하는 명령의 90 %는 단순하다"는 점을 든다. 커뮤니티 보고에는 이 혼합의 함정도 있다. 내장 해석기가 놓친 명령이 LLM으로 가서 수십 초가 걸리거나,
  LLM과 대화를 이어 가는 중에는 내장 해석기를 다시 보지 않는 경우다. **넘어간 뒤의 경로도 똑같이 정확해야 한다**는 뜻이다.
- **Windows 설정 에이전트**: 설정 전용 소형 모델(Mu)을 360만 건으로 학습해 수백 개 설정을 다룬다. 그런데도 Microsoft는 "여러 낱말의 뜻이 분명한 질의에서 가장 잘 동작하고
  짧거나 덜 쓴 입력은 맥락이 부족하다"고 보고, 짧은 질의는 종전의 검색 결과를 보여 주고 긴 질의에만 에이전트를 띄운다. 변경은 제안이고 사용자가 요청해야 적용된다.
- **Rasa CALM**: LLM은 업무 로직을 추측하지 않고 명령만 낸다. NLU 어댑터가 명령을 내면 기본값으로 LLM 호출을 건너뛰고, 둘이 충돌하면 어댑터가 이긴다.
  문서는 위험도 적는다. 분류기가 약하면 엉뚱한 흐름이 시작된다. **먼저 보는 규칙은 정밀도가 높아야 한다**는 뜻이다.
- **FunctionGemma**: Google의 수치로 기본 모델 58 %, 대상 앱의 동작으로 미세조정한 뒤 85 %. 소형 Gemma 계열은 미세조정 없이는 동작 매핑이 불안하다는 것을 만든 쪽이 말한다.
- **도구 정의 지침**: OpenAI는 한 번에 보이는 함수를 20개 미만으로(느슨한 권고), 열거형과 객체 구조로 "잘못된 상태를 표현할 수 없게" 하라고 한다.
  Anthropic은 겹치는 도구가 많으면 모델이 흐트러진다고 하고, 큰 도구 집합에는 필요한 것만 찾아 싣는 방식(내부 평가 49 % → 74 %)과 사용 예시를 권한다.
  분류(라우팅)는 "LLM으로도, 전통적인 분류기로도" 할 수 있다고 적는다. 엣지 기기 연구("Less is More", 8B 모델)도 보여 주는 도구 수를 줄이면 도구 선택 정확도가 오른다고 보고한다.
- **구조화 출력의 키 순서**: llama.cpp 변환기는 필수 속성을 스키마에 적힌 순서 그대로 고정한다(현재 소스에서 확인). Gemini 문서는 예시의 속성 순서가 스키마와 다르면
  출력이 "장황해지거나 예상과 달라질 수 있다"고 경고한다. 필드 순서가 정확도에 미치는 영향은 연구마다 엇갈리지만, 영향이 있다는 쪽은 작은 모델에서 크다고 보고한다.
  Gemma 4가 학습한 함수 호출 형식도 함수 이름이 인수보다 먼저 나온다.
- **모델의 자기 신뢰도**: 말로 표현한 신뢰도는 과신하는 경향이 여러 연구에서 반복된다.

## 3. 공통점 다섯 가지

1. **닫힌 목록은 결정적으로 먼저 본다.** 대상이 열거 가능하고 값에 타입이 있으면(기기, 설정, 인텐트) 규칙·검색·분류기가 먼저다. 모델은 그 밖을 맡는다.
2. **짧은 입력일수록 모델에 맡기지 않는다.** 전용으로 학습한 모델을 가진 Microsoft도 짧은 질의는 검색으로 처리한다. 사용자 스크린샷의 다섯 문장이 모두 짧은 꼴이다.
3. **모델은 좁은 어휘로만 말하고 실행은 코드가 한다.** 문법으로 모양을 묶고, 타입과 범위는 스키마에 넣는다.
4. **부작용은 등급을 나눠 확인한다.** 되돌릴 수 있고 근거가 분명하면 바로, 아니면 제안·확인. 모델의 신뢰도 숫자에 기대지 않는다.
5. **평가 세트로 고정한다.** 세 회사 모두 도구를 고칠 때마다 실제 문장 세트로 잰다.

## 4. 우리 앱에 대입하면

지금 구조: 슬래시 명령만 규칙, 나머지는 모델 호출 두 번(계열 선택 → 플랜). 설정 변경은 확인 대상이 아니어서, 모델이 스스로 적은 신뢰도가 기준값을 넘으면(스크린샷에서는 0.95) 바로 실행된다.

| | 가: 문법만 고치고 모델에 맡김 | 나: 설정 문장은 규칙 먼저 | 다: 세 겹(권장) |
|---|---|---|---|
| 짧은 설정 문장의 정확도 | 미세조정 없는 4B급 모델에 달림. 실모델로 재 보지 못함 | 표에 있는 이름이면 확정 | 표에 있는 이름이면 확정, 나머지는 모델 |
| 틀렸을 때 | 엉뚱한 설정이 조용히 바뀜 | 규칙이 질문을 명령으로 오해할 수 있음 | 근거 없는 변경은 확인 카드 |
| 응답 시간 | 모델 호출 2회. 기록된 수치로 GPU 1~3초, CPU 10초 안팎 | 즉시 | 흔한 꼴은 즉시 |
| 모델이 없을 때 | 설정을 말로 바꿀 수 없음 | 가능 | 가능 |
| 2026-11-09 결정과의 관계 | 그대로 | 예외가 넓음 | 좁은 예외 하나 + 사후 안전장치 |
| 손댈 곳 | 스키마 직렬화, 예시 | 규칙 확장 | 스키마, 검증 한 곳, 카탈로그 맞춤기 |

"가"의 약점은 문법을 고쳐도 남는다. 문법은 **모양**만 보장하고 **고른 설정이 맞는지**는 보장하지 않는다. FunctionGemma의 수치와 Microsoft의 판단이 그 부분을 가리킨다.
"나"의 약점은 2026-11-09에 겪은 것과 같다. 그래서 "다"는 규칙을 문장 전체 일치로 좁히고, 모델 쪽에는 검증을 붙인다.

## 5. 권장안 상세

**0. 문법·프롬프트 (PLN-1)**
- 플래너 스키마와 예시 응답을 순서를 지키는 직렬화로 내보낸다. op 객체는 `op`가 첫 키, 최상위는 `operations`가 `confidence`보다 먼저.
- `set_setting`의 값을 키별 타입으로 묶는다(정수 범위, 참·거짓, 열거). 지금은 46개 키 열거 + 아무 값이다.
- 프롬프트에 `키 = 한국어 라벨` 표와 `set_setting` 예시 2~3개를 넣는다.
- 테스트: "모든 op 대안의 첫 속성이 op". 실엔진 CI에 설정 문장 한 건.

**1. 완전 일치 빠른 경로 (설정 카탈로그의 키와 프로파일에 한정)**
- 조건을 모두 만족할 때만 잡는다. ① 문장에서 설정 이름(라벨·별칭·동의어)을 하나만 찾음 ② 남은 부분이 그 키의 타입으로 읽히는 값 하나와 "바꿔줘"류 어미·조사뿐
  ③ 값이 범위 안 ④ 물음이 아님("뭐야", "알려줘", "?").
- 하나라도 어긋나면 모델로 넘긴다. 범위 밖 값은 실행하지 않고 범위를 알려 준다("UI 배율은 90~150 %").
- 이름만 있고 값이 없으면 현재 값과 설정 위치를 보여 준다(VS Code·Windows 방식).
- 동의어는 카탈로그에 열로 둔다(화면 배율·글자 크기·확대, 해상도·DPI 등). 규칙 파일에 문장을 늘리지 않는다.
- 테스트: 사용자 문장 5개와 변형을 골든셋에 넣고, 질문·붙여 넣은 글이 잡히지 않는지 반례도 넣는다.

**2. 모델** — 그 밖의 모든 문장. 지금과 같다.

**3. 사후 검증 (확인 없이 실행되는 모든 op)**
- 설정·테마·언어·프로파일·모델 변경은 op의 대상 이름과 값이 문장에 근거가 있어야 바로 실행한다. 숫자는 문장에 그 숫자가 있어야 한다.
- 근거가 없으면 확인 카드로 바꾼다. 스크린샷의 경우("배율 130" → 프로파일 균형)는 "프로파일"도 "균형"도 문장에 없으므로 여기서 걸린다.
- `noop`뿐인 플랜은 카드 없이 한 줄로 답한다(USR-3).

**4. 결과 표시** — "UI 배율 100 % → 130 %"와 되돌리기 버튼.

**5. 평가** — 1번은 단위 테스트로 고정. 실제 Gemma 모델의 정확도는 이 환경에서 잴 수 없어 사용자 PC 체크리스트에 설정 문장 세트를 둔다.

## 6. 권하지 않는 것

- **낱말 포함 규칙의 부활**: 2026-11-09에 걷어낸 방식이다.
- **모델 미세조정**: 효과는 크지만(58 % → 85 %) 레지스트리의 공개 GGUF를 그대로 쓰는 지금 구조와 맞지 않는다.
- **llama-server의 네이티브 도구 호출로 전환**: Gemma 4 형식의 파서 지원이 빌드마다 다르다는 보고가 있다. 엔진 태그를 올릴 때 다시 본다.
- **신뢰도 숫자로 자동 실행 여부를 정하는 것**.

## 7. 확인하지 못한 것

- 실제 Gemma 4 모델로 문법 수정 뒤의 정확도를 재지 못했다. "가"가 충분한지는 실모델 측정으로만 확정할 수 있다.
- 이 세션의 네트워크 정책으로 원문 사이트 여럿을 직접 열지 못했다(blogs.windows.com, rasa.com, ai.google.dev, blog.google, www.home-assistant.io).
  Home Assistant 글, llama.cpp 소스와 문서, MCP 명세는 GitHub의 원문으로 확인했다. 나머지는 검색 결과 요약에 의존했고 표에 "검색 요약"이라고 적었다.
